# 0018 多人邀请码与可追加名额

2026-10-09，用户要求一个邀请码邀请多个用户，设置人数上限，并能增加已发出邀请码的名额。

新邀请默认保持 1 人，管理员创建时可设置 1 至 10000 人。管理页面显示已用、上限、剩余与可用/用满/吊销状态。对尚未吊销的旧链接可追加正整数名额，总上限不超过 10000；追加不更改 token/hash/链接、不扣减已用人数，用满链接可重新使用。已吊销链接不能通过追加恢复。

消费通过 SQLite 原子 batch 完成：仅在容量可用且未吊销时插入用户归因，紧接着根据同连接 changes() 判断本次是否插入成功，成功才增加计数。用户 id 全局唯一，因此一个用户不能重复占用同一条或另一条邀请的名额。两条语句在同一事务内，无 JS await 持锁窗口，失败整体回滚；旧用户正常登录仍直接放行。消费保持先于创建租户，避免竞争失败者留下无邀请可进入的孤儿租户。

0020 迁移为 invites 增加 max_uses（默认 1）和 used_count（默认 0），新建 invite_redemptions 保留多用户归因。历史已消费邀请计为 1 次；未消费计为 0 次；吊销状态与原 token 哈希保持。历史同用户多条消费记录在归因表保留最早一条，各条历史邀请码仍保持已使用次数，旧列保留历史证据。迁移仅准备脚本，开发验证使用仓库内临时测试库，本轮不迁移现有本地库或生产库。

接口为创建时的 maxUses 和 POST /api/admin/invites/:id/capacity 的 additionalUses，严格共享 Zod 校验并要求原管理员 RBAC。追加用 SQL 增量更新避免并发覆盖。失败、列表加载异常与非法容量在管理页显式呈现；完整原始链接仍仅在创建时返回，不为了追加名额保存 raw token。
