# 0005 — 口头禅系统：宠物个性第三维度 + 领养仪式

宠物是**猫**（IP 定制/形象全链路），但 agent prompt 自称"电子流浪狗"（react.ts:199），导致所有 speak 以"汪!"/🐕 开头——人设矛盾 + 话语单调。修人设 + 把"口头禅"做成宠物个性第三维度（性格行为 + 口头禅说话标识 + 形象视觉）。

## 决策

**1. 猫人设修复（A）+ 形象不硬塞（C 收窄）**：react.ts"电子流浪狗"→"电子流浪猫"，"汪!"示例→"喵!"。形象细节（红围巾/配色）**不注入 prompt**——由 IP 定制/表情包视觉链路承载，避免"戴红围巾的橘猫"硬塞进 system prompt 的怪异感。物种维度不建模（默认猫，口头禅已承载个性化，species 字段是重复建模）。

**2. 口头禅建模**：pet 加 `catchphrases`: `[{text, weight}]`（默认均匀 3-4 条，纯文字不带 emoji——emoji 交 LLM 自然发挥，现有 🐕 泛滥已是教训）。默认组放 shared 性格注册表（与 tonePrompt 并列，单一真相源）：好奇 `咪?这是什么呀/喵——让我看看/咦?有意思`、活泼 `喵喵喵!/喵呜——冲!/快来看快来看`、慵懒 `呼噜…/喵…(打个哈欠)/嗯…再说吧`、沉稳 `喵。/嗯,知道了/此事值得一记`。演化历史落盘记录（暂不展示，可扩展）。

**3. prompt 注入：纯 prompt + 尾部低频重写（成本约束驱动）**：口头禅段放 system prompt **固定段末尾**，重写仅发生在进化事件（反馈/反思，天级低频）。不代码拼接（双机制混乱），不每轮随机挑（无谓破坏缓存）。配合 prompt cache 优化（issue #113：固定段前置、动态段后置），前缀缓存命中不受口头禅重写影响。

**4. 领养仪式（4 步，每步 AI 候选 + 可编辑）**：起名 → 选性格（4 卡纯自选，**无 AI 推荐**——性格注册表固定 4 型，LLM 推荐是假仪式）→ 口头禅 → 选兴趣。起名/口头禅步：LLM **一次返回 3 候选**（JSON 解析拆分），依赖上一步上下文即时生成（口头禅依赖名字+性格）；"换一批"每步限 3 次（限流，防成本滥用）。交互文案营造"领养宠物"感。

**5. 进化：反馈归因（A 起步→C）**：复用 feedback-pipeline，主人点赞/踩 speak → 除兴趣归因外，权重归因到该条 speak 用过的口头禅；权重下限 0.05（防某条被踩到消失）。反思自我调节（宠物嫌"喵!说太多"自动降权）记后续，跑出数据再上。

## Considered Options
- **纯 prompt 引导 vs 代码挑+poll 用 vs 代码拼接**：拼接机械突兀、LLM 语义断裂；代码挑+prompt 用双机制混乱；纯 prompt 单一真相源 + 尾部低频重写，缓存友好 → 纯 prompt。
- **每步即时生成 vs 一次生成全套**：步骤间有上下文依赖（口头禅依赖名字+性格），一次生成失去连贯；即时生成认领一次 3-4 次调用，认领是低频操作，成本可接受 → 即时。
- **每步 1 默认 vs 3 候选**：3 选 1 + "换一批"是领养游戏感核心交互，符合"让用户有领养宠物感觉" → 3 候选（一次调用拆 3，换批限 3 次）。
- **性格步 AI 推荐 vs 纯自选**：性格是行为绑定注册表，推荐是假仪式且无实际收益 → 纯自选。
- **物种字段 species vs 口头禅承载**：默认猫，口头禅已能表达物种特征，species 是重复建模 → 不建。

## Consequences
- react.ts prompt 结构随 issue #113 一并重构（固定段前置），口头禅段在固定段末尾；组装顺序需测试守护（固定前缀不因动态内容位移）。
- pet 数据模型加 catchphrases + 演化历史存储；认领/设置 API 扩展（GET/PUT catchphrases）。
- web：口头禅仅设置页编辑，无首页/进化页展示。
- speak 历史记录需带上"用过的口头禅"（供反馈归因反查，同 matchedTopics 模式）。
- LLM 生成候选失败降级本地模板（领养不阻塞）；"换一批"超 3 次禁用并提示。
